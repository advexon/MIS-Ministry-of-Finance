## Historical loan application functional audit — 25 October 2026

**Verdict at audit time: not fully functional end to end.** This audit inspected the active intake, saved drafts, list/detail, package, workflow route and signature route against live Supabase columns, restrictive/permissive policies, constraints and trigger/function definitions. Earlier passing scheme/committee checks do not establish completion of the whole application module.

### Fixed and verified
- `app/dashboard/loans/new/page.tsx`: draft restoration now restores all 50 saved form fields, including customer code, establishment year, representative TIN/country, product, frequency/method, dates, financial inputs, covenants and guarantors. Explicit empty values, false, zero strings and missing legacy defaults are preserved. Previously only 28 fields were restored.
- `scripts/verify-ui-lifecycles.mjs`: executes the actual restoration callback, derives the current saved-field inventory and verifies every field, cleared values and legacy defaults.
- Authenticated Super Administrator browser acceptance at 1488×692 light reproduced a personal synthetic draft losing customer code/year before the fix; after the fix, continuing the same saved draft restored both exact values. The fixture was deleted through the confirmation dialog and a full reload confirmed its absence and preservation of the one pre-existing draft. No real application, borrower, financial record, account assignment or policy was changed. No migration was applied.

### Confirmed remaining defects from source/live metadata
1. **P1 — Intake does not persist everything it collects.** In `loans/new/page.tsx`, `handleSubmit` writes only `borrowerData` and `appData`. Visible establishment year/business description, representative passport, application/bank-approval dates, repayment method, guarantee type, purpose details, turnover/net income/exposure/risk, collateral and covenants are omitted. There are no subsequent evidence writes for them. Some have no matching live parent-table column; do not silently invent mappings or treat saving a draft as submitting these values. `productId` has no selection control; the visible Individual/Blanket control changes a different, unpersisted value. Submission falls back to 50% coverage in client code rather than obtaining an explicit configured policy.
2. **P1 — Intake is a split, non-idempotent transaction.** Borrower update/insert precedes application insert; a refused application can leave a changed/new borrower. The separate client `audit_trail` insert ignores its returned error. Each retry generates a fresh random tracking reference, and successful creation does not retire the saved draft. The database history trigger records application creation atomically, but that does not make borrower/application/audit creation one transaction.
3. **P1 — Legacy detail actions conflict with the current workflow.** `loans/[id]/page.tsx` still offers an analyst `Mark as Received` action that writes `submitted -> under_review`; the live guard permits `submitted -> uko_registration/cancelled` instead. Its legacy issuance action is shown to analysts even though `generate-guarantee` delegates to the signing-authority RPC; the canonical `SignatureReviewPanel` is a different path. The legacy claim handler inserts a claim and then directly transitions the parent to `claim_pending`, although the installed claim-submission trigger already owns that transition. Consolidate these actions instead of loosening database guards.
4. **P1 — Returned terms cannot be corrected from the current screens.** `LoanPackage` offers bank explanation and attachments for `docs_incomplete`, not editable application terms. The register's Manage link returns to the same detail page; there is no application edit route. The database allows originating-bank term corrections in draft/returned states, but a corresponding form is missing. Package controls also exclude Super Administrator even though the approved authority is broader.
5. **P1 — Post-issuance lifecycle authorization needs hardening and acceptance.** The installed `cgf_private.guard_pipeline` returns early for post-issuance/outcome statuses, without the pre-issuance transition/actor checks; it also permits same-status financial term edits for these statuses. The other installed loan triggers protect specific Director/signature/claim transitions, not a complete disbursement/rescheduling/default/settlement state machine. Ordinary Fund staff have broad loan UPDATE scope. This is a confirmed gap in the inspected guard definitions, not a claimed exploit or a passed negative-role mutation test; no real issued records were changed to test it. No composite branch/bank constraint was found either.
6. **P2 — False success and hidden query failures.** Detail `transition` does not request/confirm the affected row or match the loaded status, lacks try/finally for rejected requests, and does not await refresh. The legacy claim handler can announce success after its extra transition failed. Register and detail ignore their SWR query errors, displaying an empty list/not-found instead; intake reference queries ignore returned errors. Borrower-search errors are ignored and matching is capped at 200 borrowers. Draft deletion also lacks exact returned-ID confirmation.
7. **P2 — Register coverage is incomplete.** The status selector omits all current intermediate scheme statuses; pending counts recognize only submitted/legacy under-review. Active/pending counts use the current page, while the Total (this page) value is the full filtered count. Several controls lack accessible names. These remain unresolved, not silently certified by the successful seven-row register load.

## Historic audit findings

The entries below describe earlier fixes, not a guarantee that the current repository is error-free. Full TypeScript checking now passes: the 51 implicit-any diagnostics were caused by `ReturnType<typeof createBrowserClient>` erasing the singleton client's generic inference; an explicit `SupabaseClient` type fixes the source rather than adding loose callback annotations.

### Security — RLS gap [FIXED]
`access_logs` and `guarantee_letters` were the only tables with `relrowsecurity = false`. Fixed in `scripts/018_enable_rls_access_logs_guarantee_letters.sql`. Browser, server and proxy clients use the public key and rely on RLS. User-management APIs use a separately authorized service-role client; committee, deputy and signature RPCs use checked `SECURITY DEFINER` transactions with a pinned search path. Their authorization checks are part of the security boundary, not a substitute for ordinary table RLS.
- `access_logs`: append-only. INSERT open (`WITH CHECK true`) so failed/unauthenticated attempts still log; SELECT limited to `super_admin`/`auditor`; no UPDATE/DELETE.
- `guarantee_letters`: bank users see only their own bank's letters (via `loan_applications.bank_id`), PRSF roles see all; INSERT authenticated; UPDATE (revocation) admin-only; no DELETE.

### Bug — Borrowers City column blank [FIXED]
Read `b.city` but the column is `address_city`.

### Role names rendered blank everywhere [FIXED]
The `roles` table has no `name` column (only `name_en`/`name_ru`/`name_tj`), so every `role.name` read was `undefined` — 9 sites across `roles/page.tsx` and `admin/role-assignment.tsx`, including audit-log payloads. Now uses `lib/utils/localized-name.ts`.

### Rules-of-Hooks violation in roles page [FIXED]
`roles/page.tsx` returned early on the access check *before* its `useState` calls, changing hook order as `userRole` resolved. Guard moved below all hooks.

### Calendar component on dead v8 API [FIXED]
`components/ui/calendar.tsx` used react-day-picker v8 keys (`day_selected`, `nav_button`, `head_row`, `IconLeft`/`IconRight`) against installed v9, so custom arrows and most styling silently never applied. Ported to v9 (`selected`, `button_previous`, `weekdays`, orientation-aware `Chevron`).

### Supabase joined relations [FIXED]
PostgREST returns embeds as arrays; code cast them straight to objects, so `dashboard` bank/borrower names silently fell back to `Unknown`/`—`. Normalized via `lib/utils/supabase-relation.ts` (`one()`). `guarantee-reports` also declared `banks: { name }` while selecting `name_en`.

### Submission failed with 23502 on `customer_code` [FIXED]
"Bank Customer Code" is an optional form field, but `borrowers.customer_code` was `NOT NULL` with no default, so every application submitted without a bank code was rejected. Fixed in `scripts/019_borrowers_customer_code_optional.sql` (UNIQUE retained — Postgres allows multiple NULLs).

Two related problems fixed in the same pass:
- **Silent cross-customer overwrite.** The submit handler looked up an existing borrower by `customer_code` and then ran `.update()` on that row, so entering a code already owned by a *different* customer overwrote that customer's name/TIN/address. Now blocked with a clear message. Identity lookup is by TIN only.
- **Raw Postgres JSON shown to users.** `err instanceof Error ? err.message : JSON.stringify(err)` leaked driver JSON, because Supabase errors are plain objects, not `Error`s. New `lib/utils/db-error.ts` maps SQLSTATEs (23502/23505/23503/23514/22001/22P02/42501) to actionable text and never returns JSON. Reusable for other forms.

**Open question:** `customer_code` is UNIQUE *globally*, but it is a per-bank reference and `borrowers` has no `bank_id`. Two banks cannot both use their own code `42` for different customers — needs a product decision (scope per bank vs. drop uniqueness).

### Draft completion never reached 100% [FIXED]
Hardcoded list counted 5 optional fields (`addressStreet`, `city`, `phone`, `legalRepBirthdate`, `passportNumber`) as required and missed `legalRepTin`, capping completion near 72%. Now derived from `REQUIRED_FIELD_NAMES` in `use-loan-form-validation.ts`, so it cannot drift from the form's own validation.
